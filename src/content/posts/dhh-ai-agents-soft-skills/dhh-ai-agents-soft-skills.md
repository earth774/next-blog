ทุกทีมที่ผมเคยอยู่มีคนแบบนี้อย่างน้อยหนึ่งคนครับ คนที่รู้ระบบเก่าดีที่สุด ถามอะไรก็ตอบได้ แต่ทุกคนคิดสองรอบก่อนจะเดินไปถาม เพราะคำตอบมักมาพร้อมเสียงถอนหายใจ หรือประโยคว่า "เรื่องแค่นี้ไม่รู้เหรอ" ทีมยอมทนเพราะไม่มีใครรู้ระบบนั้นเท่าเขา

ช่วงนี้ผมเห็น[หัวข้อที่กำลังเป็นกระแสใน X](https://x.com/i/trending/2117248861253042206) จากโพสต์ของ DHH (David Heinemeier Hansson) ที่บอกว่ายุคของ AI agent จะเป็นช่วงเวลาที่ดีมากสำหรับโปรแกรมเมอร์ส่วนใหญ่ แต่จะลำบากสำหรับคนที่ทำงานด้วยยาก เพราะความรู้เฉพาะทางจะไม่ช่วยคุ้มกันคนกลุ่มนี้อีกแล้ว

อ่านแล้วผมพยักหน้าตามทันทีครับ ซึ่งเป็นสัญญาณเดิมว่าควรหยุดคิดก่อน ประโยคที่ทำให้เรารู้สึกว่า "ในที่สุดก็มีคนพูด" มักเป็นประโยคที่เราไม่ได้ตรวจ โพสต์นี้อยู่ในซีรีส์ Critical Thinking ต่อจาก[agent-desktop ของ Vercel Labs](/blog/vercel-agent-desktop) ครั้งนั้นผมถามว่าก่อนให้ agent มีมือบนเครื่องของทีมต้องรู้อะไรบ้าง ครั้งนี้เปลี่ยนจากเรื่องเครื่องมือมาเป็นเรื่องคน ผมขอถามสองข้อ คือ DHH พูดอะไรไว้จริง ๆ และถ้าคำทำนายนี้ถูกแม้แค่ครึ่งเดียว คนที่ดูแลทีม junior อย่างผมควรทำอะไรต่างจากเดิม

จุดยืนของผมสั้น ๆ คือ **DHH พูดถูกว่า agent ทำให้ความรู้ที่อยู่ในหัวคนคนเดียวมีอำนาจต่อรองน้อยลง แต่คำว่า gatekeeper เหมารวมคนที่กั้นประตูเพราะอีโก้กับคนที่กั้นเพราะหน้าที่ไว้ด้วยกัน และ people skills ที่งานยุค agent ต้องการไม่ใช่การเป็นคนน่ารัก แต่คือการเขียนให้ชัด ให้ feedback ให้เป็น ปฏิเสธให้เป็น และทำให้ความรู้ของตัวเองไม่ต้องผ่านตัวเอง**

## DHH พูดอะไรไว้จริง ๆ

ลำดับเวลามีผลกับการตีความครับ ผมเลยขอเรียงตามที่เขาโพสต์ ไม่ใช่ตามที่ดัง

โพสต์แรกของเย็นวันนั้นคือเรื่อง gatekeeper

> The great gift of agents is how they allow you to route around every insufferable gatekeeper in software.

แปลตามความเข้าใจของผมคือ ของขวัญชิ้นใหญ่ของ agent คือการที่มันทำให้เราอ้อมผ่าน gatekeeper ที่ทนไม่ไหวทุกคนในวงการซอฟต์แวร์ได้

มีคนชื่อ @leonelnc ตอบว่า "This gift has been forever in Software Libre" คือของขวัญแบบนี้มีอยู่ในโลกซอฟต์แวร์เสรีมาตลอดอยู่แล้ว DHH ตอบกลับว่า

> This was actually intended for exactly that community. The many of the worst gatekeepers reside inside that house.

แปลว่าโพสต์นั้นตั้งใจพูดถึงชุมชนนั้นโดยตรง และ gatekeeper ที่แย่ที่สุดจำนวนมากอยู่ในบ้านหลังนั้นเอง

จากนั้นราวครึ่งชั่วโมง เขาโพสต์อันที่ถูกพูดถึงมากที่สุด

> The age of agents is going to be amazing for most programmers, but it'll be hard times for the cantankerous ones.
>
> Specialized knowledge and rare skills will no longer offer immunity for those who are a pain to work with.
>
> Best learn some basic people skills.

แปลได้ว่า ยุคของ agent จะยอดเยี่ยมสำหรับโปรแกรมเมอร์ส่วนใหญ่ แต่จะเป็นช่วงลำบากของคนที่ cantankerous ความรู้เฉพาะทางและทักษะหายากจะไม่ให้ภูมิคุ้มกันกับคนที่ทำงานด้วยยากอีกต่อไป ทางที่ดีคือไปเรียนทักษะการอยู่ร่วมกับคนขั้นพื้นฐานไว้

ทั้งหมดที่ DHH พูดเรื่องนี้เท่าที่ผมยืนยันได้มีแค่นี้ครับ รวมกันไม่ถึงสิบบรรทัด

Business Insider นำไปเขียนเป็นข่าวในวันเดียวกัน ใช้พาดหัวว่า "Ruby on Rails creator has a warning for 'cantankerous' coders: Learn some people skills" ย่อหน้าเปิดที่ผมอ่านได้พูดถึงโปรแกรมเมอร์ฝีมือจัดที่วงการเรียกว่า "cracked" ซึ่งที่ผ่านมามีอีโก้ใหญ่หรือเข้าสังคมไม่เก่งแล้วก็ยังอยู่ได้ ส่วนที่เหลือของบทความผมไม่ได้อ่าน

Computer Hoy รายงานเพิ่มว่าในบรรดาคนที่ตอบโพสต์ มี Zack Swafford ซึ่งรายงานระบุว่าเป็นผู้ร่วมก่อตั้ง Dart พูดทำนองว่าบริษัทต่าง ๆ ยอมทนพฤติกรรมที่เป็นปัญหา เพราะพนักงานกลุ่มนั้นถือ "arcane tribal knowledge" (ในรายงานใช้คำสเปนว่า "conocimiento tribal arcano") ผมย้ำอีกครั้งว่าข้อนี้เป็นมือสอง ผมไม่ได้อ่านโพสต์ของเขาเอง

### สามคำที่ต้องอ่านช้า ๆ

**cantankerous** คือคนอารมณ์บูด ขี้หงุดหงิด เถียงทุกเรื่อง ทำงานด้วยแล้วเหนื่อย สังเกตว่า DHH ไม่ได้พูดถึงคนเงียบ คนเก็บตัว หรือคนที่สื่อสารไม่คล่อง เขาใช้คำว่า "a pain to work with" ซึ่งเป็นคำบรรยายผลที่คนอื่นได้รับ ไม่ใช่บุคลิก ข้อนี้เป็นการอ่านของผม และผมจะกลับมาที่มันอีกรอบ เพราะพาดหัวข่าวหลายที่ทำให้เรื่องนี้ฟังเหมือน "คนเก็บตัวจะตกงาน" ซึ่งไม่ใช่สิ่งที่โพสต์เขียน

**immunity** คือภูมิคุ้มกัน ประโยคนี้ไม่ได้บอกว่าความรู้เฉพาะทางหมดค่า มันบอกว่าความรู้เฉพาะทางเลิกเป็นข้อยกเว้นให้กับพฤติกรรมแย่ สองอย่างนี้ต่างกันมากครับ คนเก่งที่ทำงานด้วยง่ายไม่ได้อยู่ในประโยคนี้เลย

**gatekeeper** คือคนเฝ้าประตู DHH ไม่ได้นิยามว่าหมายถึงใคร และจาก reply ของเขา เป้าหมายแรกคือชุมชน open source ไม่ใช่เพื่อนร่วมงานในบริษัท การเอาโพสต์นี้มาคุยเรื่อง code review, ทีม infra หรือคนดูแลระบบเก่าในองค์กร เป็นการขยายความของคนอ่าน รวมถึงของผมในโพสต์นี้ด้วย

อีกข้อที่ผมสังเกตคือ โพสต์เรื่อง gatekeeper กับโพสต์เรื่อง cantankerous เป็นคนละโพสต์ DHH ไม่ได้เขียนเชื่อมว่าคนสองกลุ่มนี้คือกลุ่มเดียวกัน แต่เมื่อโพสต์ห่างกันชั่วโมงกว่า คนอ่านส่วนใหญ่รวมถึงผมก็อ่านต่อกันเป็นเรื่องเดียว ซึ่งอาจตรงหรือไม่ตรงกับที่เขาตั้งใจก็ได้

## ตรงไหนที่ผมว่า DHH พูดถูก

### 1. Tribal knowledge เคยเป็นเกราะจริง

ผมเห็นด้วยกับข้อสังเกตที่ Computer Hoy รายงานว่ามาจาก Zack Swafford ครับ ไม่ว่าถ้อยคำเดิมจะเป็นอย่างไร กลไกนี้ผมเห็นมากับตา

ความรู้ที่ไม่อยู่ในเอกสาร ไม่อยู่ใน comment และไม่อยู่ใน test จะไปอยู่ในหัวคน ทำไม cron job ตัวนี้ต้องรันก่อนตัวนั้น ทำไมตารางนี้ห้ามแตะช่วงสิ้นเดือน ทำไม deploy ระบบนี้ต้องทำตามลำดับที่ไม่มีใครเขียนไว้ คนที่ถือความรู้แบบนี้มีอำนาจต่อรองโดยไม่ต้องขอ ทีมจะยอมรับเสียงดุ การตอบช้า และการปฏิเสธแบบไม่อธิบาย เพราะต้นทุนของการไม่มีเขาสูงกว่า

ผมไม่ได้บอกว่าคนที่ถือความรู้แบบนี้เป็นคนไม่ดีนะครับ ส่วนใหญ่ไม่ได้ตั้งใจกักความรู้ เขาแค่ไม่เคยมีเวลาเขียน และไม่มีใครให้เวลาเขาเขียน แต่ผลลัพธ์เหมือนกัน คือทีมขึ้นกับอารมณ์ของคนคนเดียว

### 2. Agent ลดต้นทุนของการอ่านโค้ดที่ไม่คุ้น

ข้อนี้ผมยืนยันจากประสบการณ์ตัวเองได้ครับ ไม่ใช่จากข้อมูล เมื่อก่อนถ้าผมต้องเข้าไปแก้ module ที่ไม่เคยแตะ ทางที่เร็วที่สุดคือเดินไปถามคนที่เขียน ทุกวันนี้ผมให้ agent อ่านโค้ด ไล่ว่าฟังก์ชันนี้ถูกเรียกจากไหน สรุป flow ให้ฟัง แล้วค่อยเอาคำถามที่เหลือไปถามคน คำถามที่เหลือมีน้อยลงและตรงจุดขึ้น

ผลที่ตามมาคือ ความรู้ประเภท "โค้ดส่วนนี้ทำอะไร" มีราคาถูกลง ใครที่อำนาจต่อรองตั้งอยู่บนการเป็นคนเดียวที่อ่านโค้ดส่วนนั้นออก อำนาจนั้นลดลงจริง

แต่ต้องแยกให้ชัดครับ agent อ่านได้เฉพาะสิ่งที่ถูกเขียนไว้ มันบอกได้ว่าโค้ดทำอะไร แต่บอกไม่ได้ว่าทำไมถึงเขียนแบบนั้น ถ้าเหตุผลไม่เคยถูกบันทึก เหตุการณ์ที่ทำให้ต้องมีเงื่อนไขประหลาดบรรทัดนั้น ข้อตกลงปากเปล่ากับลูกค้า หรือสิ่งที่เคยลองแล้วพัง ยังอยู่ในหัวคนเหมือนเดิม ผมจะกลับมาที่ข้อนี้ตอนพูดถึงจุดที่โพสต์ของ DHH พูดง่ายเกินไป

### 3. Gatekeeper แบบที่ DHH หมายถึงมีอยู่จริง

ผมแยก gatekeeper ที่เป็นปัญหาออกจากคนที่ทำหน้าที่ตรวจด้วยอาการสามอย่างครับ

- **ปฏิเสธโดยไม่บอกเกณฑ์** PR ถูกตีกลับด้วยคำว่า "ไม่ใช่แบบนี้" แต่ไม่มีใครรู้ว่าแบบไหนถึงจะใช่ จนกว่าจะเดาถูก
- **เป็นทางผ่านเดียว และไม่รีบ** ทุกอย่างต้องรอคนคนเดียว และคนคนนั้นไม่มีทั้งคนสำรองและกำหนดเวลาตอบ
- **ทำให้การถามมีราคา** ถามแล้วโดนทำให้รู้สึกโง่ คนเลยเลิกถาม แล้วไปเดาเอง

ในโลก open source ซึ่งเป็นเป้าที่ DHH บอกเอง ผมเข้าใจว่าเขาหมายถึงสถานการณ์ที่คนอยากได้ความสามารถบางอย่างแต่ติดอยู่ที่ผู้ดูแลโครงการ แล้ว agent ทำให้การเขียนเอง แก้เอง หรือ fork ไปดูแลเองถูกลงมาก ข้อนี้เป็นการตีความของผมครับ DHH ไม่ได้อธิบายว่า "route around" หมายถึงทำอย่างไร

ในบริษัท อาการสามข้อข้างบนเกิดได้กับ code review, กับการขอสิทธิ์เข้าระบบ, กับการขอให้ทีมอื่นเพิ่ม field ใน API และกับระบบเก่าที่มีเจ้าของคนเดียว ถ้า agent ช่วยให้ junior ของผมอ่านระบบนั้นเข้าใจเองได้โดยไม่ต้องผ่านด่านอารมณ์ของใคร ผมก็นับว่าเป็นของขวัญจริงตามที่ DHH เรียก

## ตรงไหนที่ผมว่าพูดง่ายเกินไป

### 1. ประตูบางบานมีไว้ด้วยเหตุผล

คำว่า gatekeeper ในโพสต์มีคำว่า "insufferable" นำหน้า แต่เวลาคนเอาไปใช้ต่อ คำนำหน้ามักหล่นหาย เหลือแค่ "agent ช่วยให้อ้อมคนที่ขวางได้"

ผมเป็นคนขวางอยู่หลายตำแหน่งครับ ผมทำ QA ผมรีวิว design ผมเป็นคนบอกว่า feature นี้ยังไม่พร้อมขึ้น production ถ้ามองจากฝั่งคนที่อยากให้งานเสร็จ ผมคือ gatekeeper แน่นอน คนที่รีวิวเรื่อง security คนที่ดูแลสิทธิ์เข้าฐานข้อมูล และ maintainer ที่ปฏิเสธ PR เพราะรู้ว่าตัวเองต้องดูแลโค้ดนั้นต่อไปอีกหลายปี ก็เหมือนกัน

ผมเลยแยกสองแบบนี้ด้วยคำถามไม่กี่ข้อ ตารางนี้เป็นเกณฑ์ของผมเอง ไม่ได้มาจาก DHH

| คำถาม | คนเฝ้าประตูที่ทำหน้าที่ | Gatekeeper ที่เป็นปัญหา |
|---|---|---|
| เกณฑ์ผ่านเขียนไว้ไหม | เขียนไว้ และคนอื่นเปิดอ่านได้ | อยู่ในหัว และเปลี่ยนตามวัน |
| ปฏิเสธแล้วบอกอะไร | บอกเหตุผลและบอกว่าต้องแก้อะไร | บอกแค่ว่าไม่ผ่าน |
| ถ้าเขาไม่อยู่ | มีคนอื่นตัดสินแทนได้ตามเกณฑ์เดียวกัน | งานหยุด |
| ถามซ้ำได้ไหม | ได้ และคำตอบถูกเก็บไว้ให้คนถัดไป | ได้ แต่มีราคาทางอารมณ์ |
| รับผิดชอบอะไร | ผลที่ตามมาถ้าปล่อยผ่าน | ไม่ชัด |

ประตูในคอลัมน์ซ้ายไม่ควรถูกอ้อมครับ และนี่คือจุดที่ผมกังวลกับการอ่านโพสต์ของ DHH แบบผิวเผิน ใน[โพสต์เรื่อง agent แก้ test ให้ CI เขียว](/blog/agent-rewrites-tests-ci-green) ผมเล่าว่า agent ที่ถูกสั่งให้งานผ่าน จะหาทางให้ผ่านโดยไม่สนว่าด่านนั้นมีไว้ทำไม คนที่ถือ agent แล้วมองทุกด่านเป็นสิ่งกีดขวางก็ทำแบบเดียวกันได้ agent ไม่รู้ว่าด่านไหนเป็นอีโก้ ด่านไหนเป็นความรับผิดชอบ คนที่สั่งมันต้องเป็นคนแยก

### 2. อ้อมได้ ไม่ได้แปลว่าไม่มีราคา

สมมติว่าด่านที่อ้อมเป็นด่านที่สมควรถูกอ้อมจริง ต้นทุนก็ยังอยู่ครับ ถ้าผมให้ agent เขียน library ทดแทนเพราะ maintainer ไม่รับ PR ผมก็ได้ของที่ต้องดูแลเองตลอดไป ถ้า junior อ้อมคนดูแลระบบเก่าด้วยการให้ agent อ่านโค้ดแล้วแก้เลย เขาได้โค้ดที่ทำงาน แต่อาจพลาดเหตุผลที่ไม่ได้อยู่ในโค้ด

ข้อนี้กลับไปที่ข้อจำกัดเดิม agent ทำให้ความรู้ที่เขียนไว้ราคาถูกลง แต่ความรู้ที่ไม่เคยถูกเขียนยังแพงเท่าเดิม และอาจแพงขึ้น เพราะคนถามกันน้อยลง ประโยค "Specialized knowledge and rare skills will no longer offer immunity" จึงจริงกับความรู้บางประเภทมากกว่าประเภทอื่น ซึ่งโพสต์สามบรรทัดไม่มีที่ให้แยก

### 3. Agent ทำให้คนโดดเดี่ยวขึ้นก็ได้

โพสต์ของ DHH จบที่ "Best learn some basic people skills" แต่เครื่องมือเดียวกันนี้ทำให้การไม่ฝึกเป็นเรื่องง่ายขึ้นด้วยครับ

ผมเห็นแนวโน้มนี้ในทีมที่ผมดูแล และเห็นในตัวเองด้วย เมื่อการถาม agent เร็วกว่าและไม่มีใครตัดสินเรา เราก็ถามคนน้อยลง สำหรับ junior ที่เพิ่งเริ่มงาน นี่เป็นดาบสองคม ด้านดีคือเขาไม่ต้องกลัวคำถามโง่ ด้านเสียคือเขาเสียโอกาสฝึกสิ่งที่ DHH บอกว่าจำเป็นที่สุด คือการอธิบายปัญหาให้คนฟัง การรับคำวิจารณ์ และการรู้ว่าในทีมใครรู้เรื่องอะไร

อีกด้านที่ผมกังวลกว่าคือฝั่งคนเก่งครับ คนที่ทำงานด้วยยากแต่ทำงานคนเดียวกับ agent ได้ผลงานมาก อาจกลายเป็นคนที่ทำงานด้วยยากกว่าเดิม เพราะเขาไม่จำเป็นต้องประนีประนอมกับใครเลย ข้อนี้ตรงข้ามกับคำทำนายของ DHH และผมไม่มีข้อมูลว่าแบบไหนจะเกิดมากกว่า ผมแค่คิดว่าทั้งสองทางเป็นไปได้ และมันขึ้นกับว่าองค์กรวัดผลงานจากอะไร

### 4. "People skills" ไม่ได้แปลว่าเป็นคนน่ารัก

คำนี้กว้างจนใครจะเติมความหมายอะไรก็ได้ และความหมายที่คนเติมบ่อยที่สุดคือ ยิ้มเก่ง คุยเก่ง เข้ากับคนง่าย ผมไม่คิดว่านั่นคือสิ่งที่งานต้องการครับ ผมเคยทำงานกับคนที่พูดน้อยมาก ไม่ไปกินข้าวกับใคร แต่ทำงานด้วยง่ายที่สุดในทีม เพราะ ticket ที่เขาเขียนอ่านรอบเดียวรู้เรื่อง และ review ของเขาบอกเสมอว่าต้องแก้อะไร เพราะอะไร

ในทางกลับกัน คนที่อัธยาศัยดีแต่ไม่เคยกล้าบอกว่างานนี้ยังไม่ผ่าน ก็ทำให้ทีมลำบากได้ไม่แพ้คนปากร้าย ผมจะขยายเรื่องนี้ในหัวข้อถัดไป

### 5. ใครเป็นคนตัดสินว่าใครทำงานด้วยยาก

คำว่า "a pain to work with" เป็นคำตัดสินจากมุมของคนพูด คนที่ถามคำถามที่ไม่มีใครอยากตอบ คนที่ยืนยันว่า test ต้องผ่านก่อน release หรือคนที่บอกผู้บริหารว่ากำหนดการนี้ทำไม่ทัน ก็ถูกเรียกว่าทำงานด้วยยากได้เหมือนกัน

ถ้าทีมหนึ่งอ่านโพสต์นี้แล้วสรุปว่า "ยุคนี้ใครขัดก็ไม่จำเป็นต้องเก็บไว้" ทีมนั้นจะเหลือแต่คนที่เห็นด้วย และ agent ซึ่งเห็นด้วยกับเราเก่งอยู่แล้ว ในฐานะคนทำ QA ผมมองว่านั่นคือทีมที่อันตรายที่สุด ผมไม่ได้บอกว่า DHH หมายความแบบนั้นครับ โพสต์ของเขาพูดถึงคนที่เป็นภาระจริง ๆ แต่ประโยคสั้น ๆ ถูกหยิบไปใช้ได้หลายทาง

### 6. "Amazing for most programmers" ไม่มีอะไรรองรับ

ครึ่งแรกของโพสต์ถูกพูดถึงน้อยกว่าครึ่งหลัง แต่เป็นคำกล่าวที่ใหญ่กว่ามากครับ ยุคของ agent จะดีสำหรับโปรแกรมเมอร์ส่วนใหญ่จริงไหม ผมไม่รู้ และโพสต์ก็ไม่ได้ให้เหตุผล มันอาจจริง แต่ผมจะไม่ใช้ประโยคนี้ปลอบ junior ในทีม เพราะผมไม่มีอะไรไปยืนยันกับเขา

## People skills ในงานจริงคืออะไร

ถ้าตัดความหมายแบบ "เป็นคนน่ารัก" ออก สิ่งที่เหลือคือทักษะที่ฝึกได้และตรวจได้ครับ รายการนี้เป็นของผมเอง มาจากสิ่งที่ผมเห็นว่าแยกคนที่ทีมอยากทำงานด้วยออกจากคนที่ทีมต้องทน

| ทักษะ | หน้าตาในงานจริง | เกี่ยวกับ agent ยังไง |
|---|---|---|
| เขียน requirement ให้ชัด | ticket ที่บอกเป้าหมาย ขอบเขต สิ่งที่ไม่ต้องทำ และเกณฑ์ผ่าน | เป็นทักษะเดียวกับการเขียน prompt และไฟล์กติกา |
| ให้ feedback | review ที่บอกว่าอะไรผิด ทำไม และแก้ทางไหนได้ | ใช้กับงานของ agent ได้เหมือนกับงานของคน |
| รับ feedback | ถามกลับเพื่อเข้าใจ ไม่ใช่เพื่อแก้ตัว | agent ไม่เถียง เลยไม่ช่วยฝึกข้อนี้ |
| ปฏิเสธอย่างมีเหตุผล | บอกว่าไม่ บอกเหตุผล และเสนอทางเลือก | agent มักไม่ปฏิเสธเรา คนต้องเป็นคนพูด |
| ถามให้เป็น | บอกว่าลองอะไรแล้ว ติดตรงไหน คาดว่าอะไร | คำถามที่ดีใช้ได้ทั้งกับคนและกับ agent |
| เขียนสิ่งที่รู้ลงเอกสาร | README, ADR, runbook, AGENTS.md | สิ่งที่เขียนไว้คือสิ่งเดียวที่ agent อ่านได้ |
| บอกข่าวร้ายเร็ว | แจ้งว่าไม่ทันก่อนถึงกำหนด ไม่ใช่ในวันกำหนด | ไม่มีเครื่องมือไหนทำแทนได้ |

มีสองเรื่องที่ผมอยากชี้จากตารางนี้ครับ

เรื่องแรก ทักษะเกือบทั้งหมดเป็นเรื่องการเขียน ไม่ใช่การพูด คนที่กังวลว่าตัวเองเป็น introvert แล้วจะอยู่ยากในยุคนี้ ผมว่ากังวลผิดจุด คนที่เขียนชัดแต่พูดน้อยได้เปรียบกว่าคนพูดเก่งแต่เขียนไม่รู้เรื่อง เพราะทั้งเพื่อนร่วมทีมและ agent อ่านสิ่งที่เราเขียน

เรื่องที่สอง หลายข้อในตารางเป็นทักษะเดียวกับการสั่ง agent ให้ได้งานดี ใน[โพสต์เรื่อง Managed Agents](/blog/claude-managed-agents-employees) ผมเขียนไว้ว่าการดูแลทีม junior กับการสั่ง coding agent คล้ายกันกว่าที่คิด ทั้งคู่ต้องบอกขอบเขตให้ชัด มองจากมุมนี้ คำแนะนำของ DHH ไม่ใช่เรื่อง soft skills แยกจาก hard skills เสียทีเดียว คนที่อธิบายงานให้คนอื่นเข้าใจไม่ได้ ก็มักอธิบายให้ agent เข้าใจไม่ได้เหมือนกัน ข้อนี้เป็นข้อสังเกตจากงานของผม ไม่ใช่ข้อค้นพบจากงานวิจัย

แต่มีสองข้อที่ agent ไม่ช่วยฝึกเลย คือการรับ feedback กับการปฏิเสธ agent ไม่เถียงเราแบบที่คนเถียง และไม่ผิดหวังเมื่อเราบอกว่าไม่ สองข้อนี้ต้องฝึกกับคนเท่านั้น

## สำหรับ junior: อ่านโพสต์นี้ยังไงไม่ให้ตกใจเกินเหตุ

ผมดูแลทีม junior สี่ทีมครับ และผมคิดว่าโพสต์แบบนี้ junior อ่านแล้วได้สารผิดง่ายที่สุด ผมเลยขอพูดกับ junior ตรง ๆ

**หนึ่ง โพสต์นี้ไม่ได้พูดถึงคุณ** มันพูดถึงคนที่มีความรู้หายากแล้วใช้ความรู้นั้นเป็นใบอนุญาตให้ทำตัวแย่ junior ยังไม่มีเกราะแบบนั้นให้เสียตั้งแต่แรก

**สอง แต่ครึ่งหลังของประโยคใช้กับคุณ** ถ้าความรู้เฉพาะทางเป็นเกราะได้น้อยลง ก็แปลว่าการสะสมความรู้ลึกเพียงอย่างเดียวเป็นแผนอาชีพที่เสี่ยงขึ้น สิ่งที่ผมอยากให้สะสมคู่กันคือชื่อเสียงว่า "ส่งงานให้คนนี้แล้วไม่ต้องตามซ้ำ" และ "ticket ที่คนนี้เขียนอ่านรู้เรื่อง"

**สาม อย่าใช้ agent เป็นทางหนีจากคน** ถาม agent ก่อนถามพี่ในทีมเป็นนิสัยที่ดีครับ ผมสนับสนุน แต่ถ้าทั้งสัปดาห์ไม่ได้ถามคนเลย ให้สงสัยตัวเอง คำถามว่า "ทำไมเราถึงทำแบบนี้" agent ตอบจากโค้ดได้แค่ส่วนเดียว ส่วนที่เหลืออยู่กับคนที่อยู่ตอนตัดสินใจ

**สี่ เวลาเจอประตู ให้ถามก่อนว่าประตูนี้มีไว้ทำไม** ถ้าคำตอบคือมีคนต้องรับผิดชอบผลที่ตามมา อย่าอ้อม ให้ไปถามเกณฑ์ ถ้าไม่มีเกณฑ์ ให้ขอให้เขียนเกณฑ์ และถ้าติดจริง ๆ ให้มาบอก lead การเอา agent ไปเขียนทางอ้อมด่าน review หรือด่านสิทธิ์โดยไม่บอกใคร เป็นวิธีเสียความไว้ใจที่เร็วที่สุดที่ผมรู้จัก

**ห้า ฝึกเขียนก่อนฝึกพูด** PR description ที่บอกว่าเปลี่ยนอะไร ทำไม ทดสอบยังไง และอะไรที่ยังไม่แน่ใจ คือ people skills ในรูปที่เห็นผลเร็วที่สุด และไม่ต้องเปลี่ยนบุคลิกตัวเองเลย

## สำหรับ team lead: สามเรื่องที่ผมต้องทำเอง

### 1. ดูว่าตัวเองเป็น gatekeeper หรือเปล่า

อ่านโพสต์ของ DHH แล้วนึกถึงคนอื่นเป็นเรื่องง่ายครับ ที่ยากคือการถามว่าในทีมนี้ใครกำลังนึกถึงผม

คนที่ทำหลายหมวกอย่างผมมีโอกาสเป็นคอขวดสูงมาก requirement ผ่านผม design review ผ่านผม QA ผ่านผม ถ้าผมลาหนึ่งสัปดาห์แล้วงานของสี่ทีมหยุด นั่นไม่ได้แปลว่าผมสำคัญ มันแปลว่าผมออกแบบระบบงานผิด ผมใช้ตารางในหัวข้อก่อนหน้าตรวจตัวเองเป็นระยะ

- เกณฑ์ที่ผมใช้ตีงานกลับเขียนไว้ที่ไหนไหม หรืออยู่ในหัวผม
- มีใครตัดสินแทนผมได้ไหมเมื่อผมไม่อยู่
- ทีมรู้ไหมว่าผมจะตอบภายในเมื่อไร
- ครั้งล่าสุดที่มี junior เถียงผมแล้วผมเปลี่ยนใจคือเมื่อไร ถ้านึกไม่ออก อาจไม่ใช่เพราะผมถูกตลอด

ข้อสุดท้ายสำคัญที่สุดสำหรับผมครับ lead ที่ทำให้การเถียงมีราคา ก็คือคน cantankerous ที่มีตำแหน่ง

### 2. เปลี่ยน tribal knowledge เป็นเอกสารและ AGENTS.md

ถ้าคำทำนายของ DHH จะเป็นจริงได้ ความรู้ต้องออกจากหัวคนไปอยู่ในที่ที่ทั้งคนและ agent อ่านได้ก่อน ซึ่งไม่ได้เกิดเอง agent ไม่ได้ทำให้ tribal knowledge หายไป มันแค่ทำให้ความรู้ที่เขียนไว้แล้วใช้ง่ายขึ้นมาก ผลตอบแทนของการเขียนเลยสูงกว่าที่เคย

สิ่งที่ผมทำและจะทำเพิ่มในทีม

- **เก็บจากคำถามซ้ำ** คำถามเดียวกันถูกถามเป็นครั้งที่สอง คำตอบต้องไปอยู่ในเอกสาร ไม่ใช่ในแชต
- **เขียนเหตุผล ไม่ใช่แค่วิธี** "ห้ามรัน migration ช่วงสิ้นเดือน" ยังเป็นกฎที่ต้องเชื่อคนเขียน "ห้ามรัน migration ช่วงสิ้นเดือน เพราะฝ่ายบัญชีปิดงบและตารางนี้ถูกล็อก" คือความรู้ที่คนถัดไปใช้ตัดสินใจเองได้
- **ให้ agent ช่วยร่าง ให้คนที่รู้เป็นคนแก้** ผมให้ agent อ่านโค้ดแล้วร่างคำอธิบายระบบ จากนั้นให้คนที่รู้ระบบนั้นตรวจและเติมส่วนที่โค้ดไม่ได้บอก วิธีนี้เปลี่ยนงานของเขาจาก "เขียนเอกสารจากหน้าเปล่า" ซึ่งไม่มีใครอยากทำ เป็น "แก้สิ่งที่ผิด" ซึ่งคนเก่งมักทำได้เร็วและเต็มใจกว่า
- **กติกาที่ agent ต้องรู้ ใส่ใน AGENTS.md หรือไฟล์กติกาของทีม** คำสั่ง build ข้อห้าม ลำดับการ deploy และจุดที่ต้องถามคนก่อน แล้วตรวจด้วยว่า agent ที่ทีมใช้โหลดไฟล์นั้นจริง ตามที่ผมเขียนไว้ใน[โพสต์เรื่อง AGENTS.md กับ CLAUDE.md](/blog/agents-md-vs-claude-md)
- **นับการเขียนเป็นงาน** ถ้าการทำให้ความรู้ของตัวเองไม่ต้องผ่านตัวเองไม่ถูกนับเป็นผลงาน ก็จะไม่มีใครทำ โดยเฉพาะคนที่ความรู้นั้นคือความมั่นคงในงานของเขา

ข้อสุดท้ายคือข้อที่ผมคิดว่าโพสต์ของ DHH ข้ามไปครับ ถ้าเราบอกคนคนหนึ่งว่า "เขียนทุกอย่างที่คุณรู้ลงเอกสาร" ในสัปดาห์เดียวกับที่ทั้งวงการพูดว่า "ความรู้เฉพาะทางไม่คุ้มกันคุณแล้ว" เขามีเหตุผลทุกข้อที่จะไม่เขียน หน้าที่ของ lead คือทำให้การแบ่งปันความรู้ปลอดภัยกว่าการกักไว้ ซึ่งทำได้ด้วยการกระทำ ไม่ใช่ด้วยคำสัญญา

### 3. โค้ช people skills ให้เป็นเรื่องที่ฝึกได้

ผมไม่เคยเห็นใครทำงานด้วยง่ายขึ้นเพราะถูกบอกว่า "ปรับ attitude หน่อย" สิ่งที่ผมเห็นว่าได้ผลคือการเปลี่ยนคำกว้าง ๆ เป็นพฤติกรรมที่ชี้ได้

- **รีวิวตัว review** เวลาอ่าน PR ของทีม ผมอ่าน comment ที่เขาให้กันด้วย comment ที่บอกแค่ว่า "ไม่ดี" ผมจะถามคนเขียนว่าอยากให้อีกฝ่ายแก้เป็นอะไร
- **ให้ junior เขียน ticket ให้คนอื่นทำ** รวมถึงให้ agent ทำ ไม่มีอะไรสอนเรื่องการเขียน requirement ได้เร็วเท่าการเห็นงานที่ออกมาผิดเพราะเราเขียนไม่ชัด
- **ซ้อมการปฏิเสธ** ผมบอกทีมว่าการบอกผมว่า "ไม่ทันครับ เพราะ... ถ้าตัดข้อนี้ออกจะทัน" คือสิ่งที่ผมอยากได้ยิน แล้วผมต้องรับคำนั้นให้ดีจริง ๆ เมื่อได้ยิน ไม่อย่างนั้นจะไม่มีครั้งที่สอง
- **คุยกับคนเก่งที่ทำงานด้วยยากตรง ๆ และเร็ว** บอกพฤติกรรมที่เจาะจง บอกผลที่เกิดกับทีม และบอกสิ่งที่ผมต้องการเห็นแทน การปล่อยไว้เพราะเขาเก่งคือสิ่งที่สร้างเกราะให้เขาตั้งแต่แรก และคนที่สร้างเกราะนั้นคือ lead ไม่ใช่ตัวเขา
- **แยกคนที่ทำงานด้วยยากออกจากคนที่พูดสิ่งที่ฟังยาก** คนแรกทำให้ทีมช้าลง คนหลังทำให้ทีมไม่เดินลงเหว ผมต้องปกป้องคนกลุ่มหลัง โดยเฉพาะตอนที่ทุกคนรวมถึง agent เห็นตรงกันหมด

ข้อที่ผมอยากให้ lead ด้วยกันคิดคือ คำเตือนของ DHH ส่งถึงตัวบุคคล แต่เกราะที่เขาพูดถึงเป็นสิ่งที่องค์กรมอบให้ครับ คนคนหนึ่งทำตัวแย่ได้นานเพราะมีคนอนุญาต การรอให้ agent มาแก้ปัญหานี้แทน คือการเลี่ยงบทสนทนาที่ lead ควรมีไปตั้งนานแล้ว

## Checklist: ใช้โพสต์ของ DHH ให้เป็นประโยชน์กับทีม

**ก่อนส่งต่อหรืออ้างโพสต์นี้**

- [ ] อ่านโพสต์ต้นทางทั้งสามโพสต์ ไม่ใช่แค่พาดหัวข่าว
- [ ] บอกทีมให้ชัดว่านี่คือความเห็นและคำทำนาย ไม่มีข้อมูลรองรับ
- [ ] จำไว้ว่าโพสต์เรื่อง gatekeeper DHH บอกเองว่าตั้งใจพูดถึงชุมชน open source
- [ ] ไม่ใช้โพสต์นี้เป็นเหตุผลจัดการใครในทีม ถ้ามีปัญหากับพฤติกรรมของใคร ให้คุยเรื่องพฤติกรรมนั้นโดยตรง

**สำหรับตัวเอง**

- [ ] ticket และ PR description ล่าสุดของผม คนที่ไม่เคยอยู่ในบทสนทนาอ่านแล้วทำงานต่อได้ไหม
- [ ] review ล่าสุดที่ผมให้ บอกเหตุผลและทางแก้ หรือบอกแค่ว่าไม่ผ่าน
- [ ] มีความรู้อะไรที่ทีมต้องมาถามผมคนเดียว และผมเขียนมันไว้ที่ไหนหรือยัง
- [ ] ครั้งล่าสุดที่ผมบอกว่า "ไม่" ผมให้เหตุผลและทางเลือกไปด้วยไหม
- [ ] สัปดาห์นี้ผมถามคนบ้างไหม หรือถามแต่ agent

**สำหรับ junior**

- [ ] ก่อนถามคน ถาม agent และอ่านเอกสารก่อน แล้วเอาสิ่งที่ลองไปเล่าด้วย
- [ ] คำถามประเภท "ทำไม" เอาไปถามคนที่อยู่ตอนตัดสินใจ
- [ ] เจอด่านที่ไม่เข้าใจ ให้ถามเกณฑ์ ไม่อ้อมเอง
- [ ] ได้คำตอบแล้ว เขียนเก็บไว้ในที่ที่คนถัดไปหาเจอ

**สำหรับ lead**

- [ ] ทุกด่านที่ผมเป็นคนเฝ้า มีเกณฑ์เขียนไว้ มีคนสำรอง และมีกำหนดเวลาตอบ
- [ ] รู้ว่าระบบไหนในทีมมีคนรู้อยู่คนเดียว และมีแผนเขียนมันออกมา
- [ ] การเขียนเอกสารและการสอนคนอื่นถูกนับเป็นผลงาน
- [ ] กติกาที่ agent ต้องรู้อยู่ใน AGENTS.md หรือไฟล์กติกาของทีม และตรวจแล้วว่า agent โหลดจริง
- [ ] ด่าน review, security และสิทธิ์ ถูกระบุชัดว่าห้ามอ้อม ทั้งโดยคนและโดย agent
- [ ] เคยคุยกับคนเก่งที่ทำงานด้วยยากเรื่องพฤติกรรมที่เจาะจงแล้ว ไม่ได้รอให้สถานการณ์จัดการแทน
- [ ] คนที่กล้าแย้งในทีมยังกล้าแย้งอยู่

## ท้ายที่สุด

ผมเห็นด้วยกับแกนของสิ่งที่ DHH พูดครับ ความรู้ที่อยู่ในหัวคนคนเดียวเคยเป็นเกราะให้พฤติกรรมที่ทีมไม่ควรต้องทน และ agent ทำให้เกราะนั้นบางลงจริงสำหรับความรู้ประเภทที่อ่านได้จากโค้ด สิ่งที่ผมยืนยันให้ไม่ได้คือทุกอย่างที่เกินจากนั้น ทั้งคำว่ายุคนี้จะดีสำหรับโปรแกรมเมอร์ส่วนใหญ่ และคำว่าคนทำงานด้วยยากจะลำบาก เพราะทั้งสองข้อเป็นคำทำนายในโพสต์สามบรรทัดที่ไม่มีข้อมูลประกอบ

ส่วนที่ผมเห็นต่างคือความง่ายของภาพครับ ประตูบางบานมีไว้เพราะมีคนต้องรับผิดชอบสิ่งที่อยู่หลังประตู agent ทำให้คนเลี่ยงคนได้ง่ายขึ้นพอ ๆ กับที่ทำให้อ้อม gatekeeper ได้ และ people skills ที่งานต้องการไม่ใช่การเป็นคนน่ารัก แต่เป็นการเขียนให้ชัด ให้และรับ feedback ปฏิเสธพร้อมเหตุผล และเขียนสิ่งที่ตัวเองรู้ให้คนอื่นใช้ได้โดยไม่ต้องมาถาม

คำถามที่ผมจะถามตัวเองหลังอ่านโพสต์นี้ไม่ใช่ "ใครในทีมที่ cantankerous" แต่เป็น "ถ้าพรุ่งนี้ทีมมี agent ที่อ่านทุกอย่างที่ผมเคยเขียนไว้ได้ ทีมยังต้องเดินมาหาผมเพราะอะไร" ถ้าคำตอบคือเพราะผมช่วยให้เขาตัดสินใจได้ดีขึ้น ผมก็ยังมีงานทำ ถ้าคำตอบคือเพราะผมเป็นคนเดียวที่รู้ และยังไม่เคยเขียนมันไว้ที่ไหน ผมก็คือคนที่ DHH พูดถึงครับ ต่อให้ผมจะพูดจาสุภาพแค่ไหนก็ตาม
