เอกสารที่อันตรายที่สุดในโปรเจกต์อาจไม่ใช่เอกสารที่เขียนผิดครับ แต่คือเอกสารที่เขียนดีมาก ครบทุกหัวข้อ มี user story มี acceptance criteria มี edge case และไม่มีใครในทีมเคยอ่านมันจริง ๆ เลยสักคน รวมถึงคนที่เป็นคนส่งมันออกไป

เมื่อก่อนผมเขียน PRD เองแบบทุลักทุเล บางฉบับมีแค่ bullet สิบข้อกับภาพหน้าจอที่วาดในกระดาษ ไม่สวย ไม่ครบ แต่ทุกบรรทัดในนั้นผมตอบได้ว่าทำไมถึงเขียนแบบนั้น วันนี้ผมพิมพ์ requirement จากลูกค้าเข้าไปใน Claude สองบรรทัด ไม่ถึงนาทีก็ได้เอกสารยาวหลายหน้าที่หน้าตาเหมือนออกมาจากทีม product ของบริษัทใหญ่ คำถามคือ ในเอกสารนั้น มีกี่บรรทัดที่ผมตอบได้ว่าทำไม

ผมเป็นทั้ง developer, PM และ PO ที่ Mulberrysoft ดูแลทีม junior ทำงานกับลูกค้าที่ requirement แทบไม่เคยครบ และใช้ Claude, Codex กับ agent อื่น ๆ แทบทุกวัน ซีรีส์นี้เริ่มจาก[การให้ agent ทำงานแทนโดยไม่ให้มันคิดแทน](/blog/critical-thinking-agents-do-work) ต่อด้วย[วันที่คำตอบของ agent กลายเป็นความเห็นของเรา](/blog/cognitive-surrender) [หนี้ความเข้าใจที่ไม่ขึ้นบน dashboard](/blog/comprehension-debt) [เจตนาที่ agent จ่ายแทนไม่ได้](/blog/intent-debt) [สีเขียวที่ไม่ได้แปลว่าถูก](/blog/verify-and-supervision-paradox) [การล็อกสเปกก่อนโค้ดด้วย OpenSpec](/blog/openspec-lock-before-code) และล่าสุด[การให้ agent grill เราจน requirement ชัด](/blog/grill-me-requirements)

สามโพสต์หลังพูดเรื่องเดียวกันจากคนละมุม คือการตัดสินใจต้องเกิดจากคนก่อนที่โค้ดจะเกิด แต่ผมยังไม่ได้พูดถึงกับดักที่อยู่ใกล้ตัว PO ที่สุด คือเมื่อ AI ไม่ได้ช่วยเราถาม แต่ช่วยเรา "เขียน" requirement ให้เสร็จไปเลย

จุดยืนของโพสต์นี้คือ **PRD ที่ AI ร่างแล้วไม่มีใครอ่าน ไม่ใช่ requirement แต่เป็นคำเดาที่แต่งตัวเป็นมติ** และมันแย่กว่าการไม่มี PRD เลย เพราะมันทำให้ทุกคนหยุดถาม

## จุดเริ่มต้นจากโพสต์เสียดสีบน X

ผมเห็น[โพสต์ของ Shanal Aggarwal บน X](https://x.com/shanal_aggarwal/status/2113716288648560941) ที่ตั้งชื่อว่า *"The State of AI-powered Product Engineering: Built by AI, Tested by AI, Used by AI."* แล้วไล่เป็นสามเฟส

เฟสแรกคือสร้างโปรดักต์ PO ใช้ AI เขียน requirement แต่ไม่อ่าน developer ใช้ AI สร้างโปรดักต์แต่ไม่ review โค้ด เฟสสองคือ QA PO ใช้ AI สร้างลิสต์บั๊กแต่ไม่ได้ทดสอบโปรดักต์เอง developer ใช้ AI แก้บั๊กแต่ไม่อ่านลิสต์บั๊ก เฟสสามคือขึ้นระบบจริง ลูกค้าเชื่อม AI agent ของตัวเองเข้ากับโปรดักต์ แล้วให้ agent ใช้ซอฟต์แวร์แทน

บทสรุปของเขาคือ AI เขียน requirement, AI สร้าง, AI ทดสอบ, AI แก้ และตอนนี้ AI เป็นผู้ใช้คนเดียว ส่วนมนุษย์ก็ *"busy attending meetings to discuss AI productivity."*

ผมขำครับ แล้วก็หยุดขำตอนอ่านบรรทัดแรกอีกรอบ *"Product Owner uses AI to write requirements. Doesn't read them."* เพราะบรรทัดนั้นคือตำแหน่งงานผมเลย

โพสต์นี้ตั้งใจเสียดสีทั้งสายพาน แต่ผมอยากหยุดอยู่ที่ข้อแรกข้อเดียว เหตุผลง่าย ๆ คือมันอยู่ต้นน้ำ ทุกอย่างที่ตามมาในโพสต์ของเขา ทั้งโค้ดที่ไม่มีใคร review บั๊กที่ไม่มีใครอ่าน ล้วนสร้างต่อจาก requirement ข้อนั้น ถ้าต้นน้ำไม่มีเจ้าของ ปลายน้ำจะเก่งแค่ไหนก็แค่สร้างสิ่งที่ไม่มีใครตั้งใจได้เร็วขึ้น

## เอกสารที่ดูครบ แต่ไม่มีเจ้าของ

ลองนึกถึงสิ่งที่เกิดขึ้นจริงเวลาเราให้ AI เขียน PRD ครับ

เราให้ input สั้น ๆ เช่น "ลูกค้าอยากได้ระบบสะสมแต้มสำหรับร้านค้า" AI ไม่ได้ตอบกลับมาว่า "ข้อมูลไม่พอ" แต่มันทำในสิ่งที่มันถูกฝึกมาให้ทำได้ดีมาก คือผลิตเอกสารที่ **หน้าตาเหมือน PRD ที่ดี** มีหัวข้อ Goals, User Stories, Functional Requirements, Non-functional Requirements, Edge Cases, Out of Scope ครบเป๊ะ

ปัญหาคือทุกหัวข้อที่ input ของเราไม่ได้ครอบคลุม AI ต้องเติมเอง แต้มหมดอายุไหม หมดอายุกี่เดือน คืนสินค้าแล้วแต้มหายไหม มีระดับสมาชิกไหม แลกแต้มเป็นส่วนลดหรือเป็นของ ทุกข้อมีคำตอบที่ฟังขึ้นอยู่ในเอกสาร เพราะ AI เห็นระบบสะสมแต้มมาเยอะ และรู้ว่าระบบส่วนใหญ่ทำแบบไหน

แต่ "ระบบส่วนใหญ่ทำแบบนี้" ไม่เท่ากับ "ลูกค้ารายนี้ต้องการแบบนี้" ครับ

ใน[โพสต์ Intent Debt](/blog/intent-debt) ผมเขียนไว้ว่าช่องว่างใน prompt จะถูกเติมเสมอ คำถามคือใครเติมและรู้ตัวไหม PRD ที่ AI ร่างคือกรณีที่ชัดที่สุดของประโยคนั้น เพราะช่องว่างไม่ได้ถูกเติมเงียบ ๆ ในโค้ดที่ไม่มีใครเห็น แต่ถูกเติมเป็นตัวหนังสือสวย ๆ ในเอกสารที่ **ทุกคนเห็น แต่ไม่มีใครอ่าน**

และนี่คือจุดที่ผมเรียกว่า **ช่องว่างความเป็นเจ้าของ** เอกสารมีอยู่จริง มีชื่อ PO อยู่ที่หัวเอกสาร ถูกแนบใน ticket ถูกส่งเข้า repo แต่การตัดสินใจข้างในไม่มีใครเป็นคนตัดสิน AI ไม่ได้เป็นเจ้าของ เพราะมันแค่เติมรูปแบบที่น่าจะเป็น PO ไม่ได้เป็นเจ้าของ เพราะไม่ได้อ่าน ส่วน dev ก็คิดว่า PO ตัดสินแล้ว

ทุกคนชี้ไปที่คนอื่น และเอกสารก็นั่งอยู่ตรงกลางอย่างมั่นใจ

## เรื่องที่เกิดซ้ำในงานรับจ้างพัฒนา

ขอเล่าเป็นภาพรวมจากหลายงานที่ผมเห็นและทำเองนะครับ ไม่ใช่โปรเจกต์ใดโปรเจกต์หนึ่ง แต่รูปแบบมันซ้ำจนผมจำได้ขึ้นใจ

ลูกค้าพิมพ์มาใน LINE ประมาณว่า "อยากให้ลูกค้าสะสมแต้มได้ ซื้อครบแล้วเอาแต้มมาแลกส่วนลด" ผมกำลังวิ่งระหว่างสามโปรเจกต์ เลยเปิด Claude วางข้อความนั้นลงไป เติมบริบทอีกสองสามบรรทัด แล้วสั่งให้เขียน PRD ฉบับเต็ม

ได้กลับมาเป็นเอกสารยาวที่ผมกวาดตาดูหัวข้อแล้วรู้สึกสบายใจมาก มันครบกว่าที่ผมจะเขียนเองในบ่ายนั้นแน่นอน ผมแปะลง ticket แล้ว assign ให้น้อง junior คนหนึ่ง

น้องเปิดเอกสาร อ่านคร่าว ๆ แล้วทำในสิ่งที่สมเหตุสมผลที่สุดสำหรับคนที่ได้รับเอกสารจาก PO คือเชื่อมัน น้องส่ง PRD ทั้งก้อนให้ agent พร้อมคำสั่งว่า implement ตามนี้ agent ก็ทำตามอย่างซื่อสัตย์ แต้มหมดอายุใน 12 เดือนตามที่เอกสารเขียน คืนสินค้าแล้วหักแต้มคืนตามที่เอกสารเขียน มีระดับสมาชิกสามระดับตามที่เอกสารเขียน test ครบ เขียวหมด

แล้วก็มาถึง UAT ครับ

ลูกค้าถามว่าทำไมแต้มของลูกค้าเก่าถึงหายไป เพราะร้านเขาสัญญากับลูกค้าไว้ตั้งแต่ต้นว่าแต้มไม่มีวันหมดอายุ ถามว่าระดับสมาชิกมาจากไหน เพราะไม่เคยขอ และถามว่าทำไมคืนสินค้าบางส่วนแล้วแต้มถึงติดลบ

ผมย้อนไปเปิด PRD แล้วพบว่าทุกข้อเขียนไว้ชัดเจนในเอกสาร ทุกข้ออยู่ในเอกสารที่มีชื่อผมเป็นคนส่ง และไม่มีข้อไหนเลยที่ผมจำได้ว่าเคยตัดสินใจ

ส่วนที่เจ็บที่สุดไม่ใช่ตอนลูกค้าถามครับ แต่คือตอนที่น้อง junior บอกว่า "ผมทำตามเอกสารของพี่ครับ" และน้องพูดถูกทุกคำ

## ทำไม PRD ที่ไม่มีใครอ่านถึงแย่กว่าไม่มี PRD

ประโยคนี้ฟังเกินจริง แต่ผมเชื่อแบบนั้นจริง ๆ ครับ ลองเทียบสองสถานการณ์ดู

ถ้าไม่มี PRD เลย น้อง junior ได้แค่ข้อความ LINE บรรทัดเดียว น้องจะรู้สึกทันทีว่าข้อมูลไม่พอ น้องจะถาม หรืออย่างน้อย agent ที่น้องใช้ก็มีโอกาสถามกลับ ช่องว่างยังมองเห็นได้ และ **ช่องว่างที่มองเห็นได้คือช่องว่างที่ยังมีคนถาม**

ถ้ามี PRD ที่ AI ร่างแต่ไม่มีใครอ่าน ช่องว่างหายไปหมด ไม่ใช่เพราะถูกตอบโดยคนที่มีสิทธิ์ตอบ แต่เพราะถูกปิดด้วยตัวหนังสือที่ดูน่าเชื่อถือ น้องไม่ถาม เพราะเอกสารตอบไว้แล้ว agent ไม่ถาม เพราะ spec ระบุไว้ชัด ส่วนผมไม่รู้ด้วยซ้ำว่ามีคำถามอะไรค้างอยู่

ผมคิดว่ามีสามแรงที่ทำให้มันอันตรายกว่าที่เห็น

**แรงแรกคืออำนาจของรูปแบบ** เอกสารที่มีหัวข้อครบ ใช้ภาษาเป็นทางการ มี acceptance criteria เป็นข้อ ๆ ส่งสัญญาณว่ามีคนคิดมาแล้ว ยิ่งดูมืออาชีพเท่าไร คนอ่านยิ่งไม่กล้าแย้ง โดยเฉพาะ junior ที่ไม่แน่ใจว่าตัวเองมีสิทธิ์ตั้งคำถามกับเอกสารของ PO หรือเปล่า

**แรงที่สองคือ agent อ่านทุกบรรทัดจริงจัง** นี่คือส่วนที่ตลกร้ายครับ มนุษย์ไม่อ่าน PRD แต่ agent อ่านครบทุกคำ และถือว่าทุกคำเป็นคำสั่ง ข้อที่ AI ตัวแรกเติมไว้แบบ "น่าจะประมาณนี้" ถูก AI ตัวที่สองอ่านเป็น "ต้องเป็นแบบนี้" ความไม่แน่นอนหายไประหว่างทาง ไม่มีใครตั้งใจลบมัน มันแค่ไม่เคยถูกเขียนไว้ตั้งแต่แรก

**แรงที่สามคือ test ยืนยันคำเดา** ใน[โพสต์ Verify](/blog/verify-and-supervision-paradox) ผมเขียนว่าสีเขียวไม่ได้แปลว่าถูก ถ้า acceptance criteria มาจาก PRD ที่ไม่มีใครอ่าน test ที่เขียนจาก criteria นั้นก็แค่พิสูจน์ว่าโค้ดทำตามคำเดาได้แม่นยำ เรามีสายพานทั้งเส้นที่ทำงานถูกต้องสมบูรณ์ โดยมีต้นทางเป็นสิ่งที่ไม่มีใครตั้งใจ

นี่แหละครับคือสิ่งที่โพสต์ของ Shanal เสียดสีไว้ในประโยคเดียว ทุกขั้นตอนมีคนรับผิดชอบในนาม แต่ไม่มีใครรับผิดชอบในเนื้อหา

## มันคือ Cognitive Surrender ในชุดของ PO

ผมพยายามซื่อสัตย์กับตัวเองว่าทำไมถึงไม่อ่าน คำตอบไม่ใช่ขี้เกียจอย่างเดียวครับ

ส่วนหนึ่งคือเอกสารยาวเกินกว่าที่ผมจะอ่านได้ในเวลาที่มี อีกส่วนคือผมกวาดตาดูแล้วรู้สึกว่า "ก็ถูกนี่" ซึ่งความรู้สึกนั้นแหละที่อันตราย เพราะการกวาดตาแล้วไม่เจออะไรผิด ไม่เท่ากับการอ่านแล้วตัดสินว่าถูก

ใน[โพสต์ Cognitive Surrender](/blog/cognitive-surrender) ผมเขียนถึงวันที่คำตอบของ agent กลายเป็นความเห็นของเรา PRD ที่ไม่มีใครอ่านคือเวอร์ชันที่ระดับสูงกว่านั้นอีกขั้น เพราะเราไม่ได้แค่รับความเห็นของ AI มาเป็นของตัวเอง แต่เรา **เซ็นชื่อรับรองแล้วส่งต่อให้คนอื่นถือเป็นข้อตกลง**

และใน[โพสต์ Comprehension Debt](/blog/comprehension-debt) ผมพูดถึงหนี้ความเข้าใจที่สะสมเมื่อโค้ดถูกเขียนเร็วกว่าที่เราเข้าใจ PRD ที่ AI ร่างก็สร้างหนี้แบบเดียวกันที่ต้นน้ำ เอกสารยาวขึ้นเร็วกว่าที่ PO เข้าใจ และวันที่ต้องจ่ายหนี้คือวันที่ลูกค้าถามว่า "ทำไมเป็นแบบนี้" แล้วเราตอบไม่ได้

## ต่อจาก Grill Me และ OpenSpec

ถ้ามองทั้งซีรีส์ ผมว่าโพสต์นี้คือด้านกลับของสองโพสต์ล่าสุดครับ

ใน[โพสต์ Grill Me](/blog/grill-me-requirements) ผมเสนอให้ agent สัมภาษณ์เราทีละคำถามจนทุกการตัดสินใจมีเจ้าของ PRD ที่ AI ร่างให้แบบรวดเดียวคือสิ่งที่ตรงข้ามกันเลย แทนที่จะถามเรายี่สิบข้อ AI ตอบยี่สิบข้อนั้นเองแล้วรวมเป็นเอกสาร ผลลัพธ์ดูคล้ายกัน คือได้ requirement ที่ครบ แต่ต่างกันตรงที่ฉบับหนึ่งมีคนตัดสินทุกข้อ อีกฉบับไม่มีใครตัดสินสักข้อ

ใน[โพสต์ OpenSpec](/blog/openspec-lock-before-code) ผมบอกว่าข้อตกลงควรอยู่ในไฟล์ที่อ่านได้และ review ได้ คำสำคัญคือ "review ได้" ครับ ไม่ใช่ "ถูก review แล้ว" `proposal.md` ที่ agent เขียนแล้วไม่มีใครอ่านก็เป็น PRD ที่ไม่มีใครอ่านอีกฉบับหนึ่ง แค่อยู่ใน repo แทนที่จะอยู่ใน Google Docs เครื่องมือล็อกสเปกได้ แต่ล็อกความเป็นเจ้าของให้ไม่ได้

ผมเลยไม่ได้คิดว่าควรเลิกให้ AI ร่าง PRD นะครับ ตรงกันข้าม ผมยังให้มันร่างแทบทุกงาน มันเก่งเรื่องเตือนว่าเราลืมหัวข้ออะไร เก่งเรื่องเรียบเรียง เก่งเรื่องเสนอ edge case ที่ผมไม่ได้นึกถึง สิ่งที่เปลี่ยนคือผมไม่ถือว่าร่างของ AI เป็น PRD แล้ว ผมถือว่ามันเป็น **รายการคำถามที่เขียนในรูปประโยคบอกเล่า**

ทุกบรรทัดในร่างที่บอกว่า "แต้มหมดอายุใน 12 เดือน" ที่จริงคือคำถามว่า "แต้มหมดอายุไหม ถ้าหมด หมดเมื่อไร" ที่ AI ตอบแทนเราไปก่อน งานของ PO คือแปลงประโยคพวกนั้นกลับเป็นคำถาม แล้วตอบมันเองทีละข้อ

## สัญญาณว่า PRD ฉบับนี้ไม่มีใครอ่าน

ผมลองรวบรวมสัญญาณที่เจอบ่อยจากงานตัวเองและงานที่ review ให้ทีม ถ้าเจอหลายข้อพร้อมกัน ผมจะถือว่าเอกสารนั้นยังไม่มีเจ้าของ

- **PO ตอบไม่ได้ว่าทำไมบางข้อถึงเขียนแบบนั้น** ถ้าถามว่า "ทำไมหมดอายุ 12 เดือน" แล้วคำตอบคือ "AI ใส่มาครับ" ข้อนั้นยังไม่ถูกตัดสิน
- **มีตัวเลขหรือกฎธุรกิจที่ลูกค้าไม่เคยพูดถึง** ระยะเวลา เปอร์เซ็นต์ จำนวนระดับ ขีดจำกัด ตัวเลขที่ชัดเจนเกินกว่า input ที่ให้ไปคือร่องรอยของการเติม
- **ไม่มีหัวข้อ "ยังไม่รู้" หรือ "รอลูกค้ายืนยัน" เลย** requirement จากลูกค้าจริงไม่เคยครบร้อยเปอร์เซ็นต์ เอกสารที่ไม่มีคำถามค้างเลยไม่ได้แปลว่าชัด แต่แปลว่าคำถามถูกปิดไปโดยไม่มีใครรู้
- **ภาษาของเอกสารไม่เหมือนภาษาที่ทีมใช้คุยกัน** คำศัพท์ที่ไม่มีใครในทีมหรือฝั่งลูกค้าใช้ เป็นสัญญาณว่าไม่มีใครเอามันมาผ่านบทสนทนาจริง
- **เอกสารยาวกว่าเวลาที่ PO ใช้กับมัน** ถ้าเอกสารสิบหน้าถูกส่งออกไปหลังจากสร้างเสร็จห้านาที คำนวณง่าย ๆ ก็รู้แล้วครับว่าไม่ได้อ่าน
- **dev ถามคำถามที่เอกสารตอบไว้แล้ว แต่ PO ไม่รู้ว่าตอบไว้ว่าอะไร** อันนี้ผมเจอกับตัวเองและเป็นสัญญาณที่ชัดที่สุด

## นิสัยที่ผมใช้ก่อนส่ง PRD ให้ใคร

ทั้งหมดนี้ไม่ได้ซับซ้อนครับ แค่ต้องยอมเสียเวลาส่วนที่ AI ประหยัดให้ กลับมาลงตรงจุดที่มันไม่ควรประหยัด

**อ่านร่างของ AI เหมือนเป็นคนเขียนเอง** ไม่ใช่กวาดตาดูว่ามีหัวข้อครบไหม แต่อ่านทีละบรรทัดแล้วถามตัวเองว่า ถ้าลูกค้าชี้บรรทัดนี้แล้วถามว่าทำไม ผมจะตอบว่าอะไร ถ้าตอบไม่ได้ บรรทัดนั้นยังไม่ใช่ของผม

**มาร์กทุกการตัดสินใจที่ไม่ได้ตัดสินเองอย่างรู้ตัว** ผมใช้วิธีง่าย ๆ คือไล่เอกสารแล้วแปะป้ายทุกกฎธุรกิจว่าเป็นหนึ่งในสามแบบ ลูกค้าบอกมา ผมตัดสินเอง หรือ AI เติม ข้อที่เป็นแบบสุดท้ายต้องถูกยกขึ้นมาเป็นคำถาม จะถามตัวเองหรือถามลูกค้าก็ได้ แต่ห้ามปล่อยไว้ทั้งอย่างนั้น ถ้าใช้ Grill Me ร่วมด้วย ข้อเหล่านี้คือวัตถุดิบชั้นดีของรอบ grill

**ลบหรือเขียนใหม่ส่วนที่ไม่ได้อ่าน** ถ้ามีหัวข้อไหนที่ผมไม่มีเวลาอ่านจริง ๆ ผมจะลบมันทิ้งก่อนส่ง ฟังดูสิ้นเปลือง แต่หัวข้อที่ไม่มีอยู่จะทำให้คนถาม หัวข้อที่มีแต่ไม่มีใครอ่านจะทำให้คนเชื่อ PRD สั้นที่ผมเป็นเจ้าของทุกบรรทัด ดีกว่า PRD ยาวที่ผมเป็นเจ้าของครึ่งเดียวเสมอ

**เป็นเจ้าของ acceptance criteria ก่อนส่งให้ agent** ถ้าเวลามีจำกัดจนอ่านได้แค่ส่วนเดียว ผมเลือกส่วนนี้ครับ เพราะ acceptance criteria คือสิ่งที่ agent จะแปลงเป็น test และ test คือสิ่งที่จะล็อกคำเดาให้กลายเป็นพฤติกรรมของระบบ ทุกข้อใน criteria ต้องเป็นข้อที่ผมพร้อมจะยืนยันกับลูกค้าตอน UAT

**เขียนสิ่งที่ยังไม่รู้ไว้ให้ชัด พร้อมชื่อเจ้าของ** เช่น "แต้มหมดอายุหรือไม่ ยังไม่ทราบ รอเจ้าของร้านยืนยัน ผู้ติดตามคือ Earth ระหว่างนี้ห้าม implement การหมดอายุ" ประโยคแบบนี้ทำให้ agent หยุดได้ ทำให้น้องรู้ว่าต้องรอ และทำให้ผมไม่ลืมถาม

**บอกทีมตรง ๆ ว่าเอกสารฉบับนี้ผ่านการอ่านระดับไหน** ผมเริ่มเขียนบรรทัดบนสุดของ PRD ว่าส่วนไหน PO ยืนยันแล้ว ส่วนไหนยังเป็นร่างจาก AI มันเป็นการยอมรับว่าเอกสารไม่สมบูรณ์ แต่ซื่อสัตย์กว่าการปล่อยให้น้องเดาว่าทุกบรรทัดผ่านการคิดมาแล้ว

**สอนน้องให้กล้าถามเอกสารของพี่** ข้อนี้สำคัญพอ ๆ กับทุกข้อข้างบนครับ ผมอยากให้น้อง junior รู้สึกว่าการถามว่า "ข้อนี้พี่ตัดสินเองหรือ AI ใส่มาครับ" เป็นคำถามปกติ ไม่ใช่การท้าทาย และถ้าคำตอบคือ "AI ใส่มา" นั่นคือความผิดของผม ไม่ใช่ของน้อง

**ถือว่า PRD ที่ไม่มีใครอ่านแย่กว่าไม่มี PRD** เป็นกฎสุดท้ายที่ครอบทุกข้อ ถ้าผมไม่มีเวลาอ่าน ผมจะส่งข้อความ LINE ต้นฉบับของลูกค้าไปพร้อมบอกว่า "ยังไม่ได้คิดต่อ ถามก่อนทำ" ดีกว่าส่งเอกสารสวย ๆ ที่ทำให้ทุกคนเลิกถาม

## ท้ายที่สุด

โพสต์ของ Shanal จบด้วยภาพที่มนุษย์นั่งประชุมคุยเรื่อง AI productivity ขณะที่ AI ทำทุกอย่างแทน ผมว่าภาพนั้นตลกเพราะมันใกล้ความจริงเกินไป และส่วนที่ใกล้ที่สุดสำหรับผมไม่ใช่ตอนท้าย แต่คือบรรทัดแรก

AI ทำให้การเขียน PRD ถูกลงจนแทบไม่มีต้นทุน แต่การเป็นเจ้าของ PRD ไม่ได้ถูกลงตามเลยครับ มันยังต้องใช้เวลา ใช้การตัดสินใจ และใช้ความกล้าที่จะบอกลูกค้าว่า "ข้อนี้ผมยังไม่รู้" เท่าเดิม สิ่งที่เปลี่ยนคือตอนนี้เราข้ามขั้นนั้นได้ง่ายขึ้นมาก และผลของการข้ามก็ดูดีขึ้นมากจนไม่มีใครสังเกต

ความยาวของเอกสารไม่เคยเป็นตัววัดความชัดของ requirement **ตัววัดจริงคือจำนวนบรรทัดที่มีคนพร้อมตอบว่าทำไม**

ดังนั้นครั้งถัดไปที่ AI ร่าง PRD ให้ผม ก่อนจะกดส่งให้ใคร ผมจะถามตัวเองแค่ข้อเดียว ถ้าลูกค้าชี้บรรทัดไหนก็ได้ในเอกสารนี้ตอน UAT ผมจะตอบได้ไหมว่าทำไม ถ้าตอบไม่ได้ เอกสารนั้นยังไม่พร้อม ไม่ว่ามันจะดูครบแค่ไหนก็ตาม

ให้ AI ร่างได้ครับ แต่ต้องอ่านจนเป็นของเราก่อน แล้วค่อยส่งให้คนหรือ agent ลงมือ
